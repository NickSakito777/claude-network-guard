# CCBaga Network protection acceptance

This record separates repository evidence from deployment evidence. The CCBaga network source and its independent Skill are present in this checkout. No VPS, provider account, client TUN, browser route, DNS resolver or WebRTC session was inspected for this acceptance. The deployed server and real client state are therefore **unknown**.

Android is outside this acceptance scope. The reference telemetry audit covers specific macOS Desktop/CLI builds and is source evidence only; it does not establish behavior for the user's installed versions or any real network path.

## What the source establishes

- `network.py` keeps credentials in a private local config, validates the PEM/PPK/PUB pairing, passes proxy setup through SSH standard input, suppresses raw remote failure output and retrieves the import YAML over SSH. The subscription receipt remains local and contains the public HTTP URL.
- First SSH contact is now two-stage: `ssh-keyscan` lists candidate SHA256 fingerprints without authenticating; after the user confirms a provider-console match, the helper writes one key to `known_hosts.pinned` and uses strict checking. Existing `known_hosts` and subscription receipts are not deleted or rewritten.
- `network.py check` now emits a fixed sanitized snapshot of ports 443/8443, xray/sub units, UFW/nftables status, the state marker, expected config paths and ownership markers for the SSH/subscription drop-ins this script writes. Only a clean first deployment or a marker-backed rerun is eligible. Legacy/unmarked state, unknown listener ownership and other conflicts stop before deployment. The snapshot reads facts; it does not prove that a provider firewall or host matches those facts.
- The Skill-driven deployment passes an empty `DIRECT_DOMAINS` value to `setup-vps.sh`. The generated server policy routes ordinary TCP through the authenticated SOCKS outbound, blocks UDP/private destinations/BitTorrent, and has no direct fallback for that TCP route. The script's standalone default still contains legacy direct domains; do not run it outside the Skill's explicit wrapper and authorization flow.
- `setup-vps.sh` now refuses direct execution unless the staged wrapper injects its preflight marker after host-key pinning, ownership classification and explicit `deploy --confirm`. The marker prevents accidental bypass of that order; it is not a security boundary against a root administrator who intentionally edits or invokes the payload.
- The generated client profile sets `ipv6: false`, `udp: false`, and omits `DIRECT` from its AI and PROXY selector groups. It intentionally directs listed domestic domains and bootstrap resolver IPs. Those fields describe generated configuration only; they do not prove that an OS, client, browser or application enforces the intended path.
- Server-side Xray DNS now uses route-following `https://1.1.1.1/dns-query`; because the resolver is a literal IP, querying that resolver needs no hostname bootstrap. With the configured TCP-to-home rule, these DoH requests enter the routing system. Project X documents that `https+local://` bypasses routing and leaves through Freedom directly, so this source no longer uses that local mode ([Xray DNS configuration](https://xtls.github.io/en/config/dns.html)). The configured `HOME_HOST` SOCKS endpoint is a separate dependency: an IP needs no DNS lookup, while a hostname needs its own bootstrap resolution before connecting to the proxy. The source passes either input through unchanged and does not prove that endpoint bootstrap uses the protected DoH path ([Xray outbound proxy resolution](https://xtls.github.io/en/config/outbound.html)). Whether the real server routes DoH through the residential SOCKS remains a live acceptance item.
- The server opens TCP 22, 443 and 8443 in UFW and denies inbound traffic by default. The script does not verify a cloud-provider firewall, every existing nftables rule, or all IPv6 behavior. The subscription service is plain HTTP on port 8443; its random path is a bearer token, not encryption. The SSH-retrieved local YAML is the preferred import path.
- The deployment is not an atomic transaction. It makes system/package, SSH, firewall and service changes; failures can leave partial state. It keeps a root-only identity file and per-file backups, but those are not a complete rollback of packages, firewall rules or remote services.
- CCBaga's app network page only generates the public Skill installation/invocation prompt; it does not run SSH or deploy. Its separate browser exit page uses the browser's current route and reports failure when all configured probe services fail. Neither page establishes that another app's traffic is protected.

## Required real-environment evidence

| Area | Acceptance steps | Evidence required to mark passed |
|---|---|---|
| First SSH trust | Run `identity` once and record the candidate fingerprint. Compare the exact SHA256 fingerprint and key type with the VPS provider console. Only after a match, rerun with `--host-key-fingerprint`; then perform the root/OS probe. On later runs, confirm strict checking succeeds. Use a disposable host to test changed-key rejection; do not rotate a production host key as a test. | Provider-console fingerprint, sanitized helper output, private `known_hosts.pinned` mode/ACL, and a later strict-check result. If the provider cannot supply an independent fingerprint, stop before authenticating. |
| Server conflict snapshot | Run `check` after pinning the host. Review `SERVER_PREFLIGHT`: a first deployment must show free 443/8443, absent services/state/config/drop-ins and no active UFW/nftables policy; a rerun must show the product marker, marked owned drop-ins, and any occupied listener must belong to the expected systemd unit. On an active-UFW rerun, review its existing rules and defaults because the snapshot reports status only. Any conflict or unknown value means stop and inspect read-only server/firewall state before approval. | The sanitized snapshot plus a reviewed, secret-free view of current service and firewall state. Do not copy `/etc/xray-setup.env` contents into logs. |
| Server configuration and firewall | After separate approval for the actual host, deploy only to an authorized Debian 12/13 target. Check `xray run -test`, xray/sub service state, UFW defaults and TCP rules, current SSH key login through a new session, and the provider's network ACL. Verify no unexpected UDP listener/rule is exposed and that 8443 is intentionally public only if the user accepts the HTTP subscription risk. | Redacted command results, service/config status, UFW plus provider-firewall evidence, and confirmation that the prior SSH session/provider console remained available during SSH hardening. |
| IPv4/IPv6 and TCP/UDP routing | From the real client, test intended TCP destinations over the active TUN and compare the observed IPv4 exit with the fixed expected residential IP. If IPv6 is available, use IPv6-capable test endpoints and inspect the host/client route and firewall while the tunnel is active. Test an allowed UDP destination separately; a TCP `curl` result cannot establish UDP blocking. In a disposable setup, make the home SOCKS unavailable and confirm protected TCP fails closed instead of leaving from the VPS. | Client version/OS and TUN status; observed IPv4 and IPv6 results; an actual UDP test; and a fail-closed result from a disposable environment. YAML flags and a server-side SOCKS probe alone do not pass this area. |
| DNS | With the real TUN enabled and System Proxy off, test system DNS and the target browser separately. Use a unique controlled hostname and resolver-side query evidence, while observing the active interface or client DNS logs. Confirm which bootstrap and listed domestic domains intentionally resolve directly, confirm protected/AI names use the configured proxy path, and confirm server-side Xray DoH leaves through the home SOCKS route. Repeat in a disposable setup with both IP and hostname SOCKS endpoints: record endpoint-host resolution as bootstrap, separately from protected destination queries. Check browser DoH settings because they can bypass the client resolver policy. | Timestamped resolver or authoritative-query evidence, client/system DNS logs or a bounded packet capture, and browser-specific DNS results. An IP echo page, a profile field, or the `tun-check` curl probe is insufficient. |
| WebRTC and browser | Import the local YAML into the actual supported Mihomo client, select the node, enable TUN, leave System Proxy off, and leave CCBaga-B's explicit proxy empty. Use a real browser WebRTC/ICE candidate test and separately verify the browser's observed exit and DNS. Check the candidate list for the user's public IPv4/IPv6 addresses; do not infer this from an ordinary IP page. | Browser/client versions, TUN and proxy settings, sanitized ICE candidate results, browser exit observation and the separate DNS result. The current built-in CCBaga browser verification does not independently prove DNS or WebRTC leak resistance. |
| Claude Desktop/CLI process egress | Record the installed app and version. With TUN active, exercise the installed Desktop and CLI separately and inspect process-level destination, DNS, IPv4/IPv6 and route evidence, including model, update and event traffic that the installed build actually produces. A source audit of a different version, CCBaga's own browser probe, and a system `curl` result do not prove those processes use the intended exit. | Per-process route/connection evidence tied to app version, observed exit, resolver evidence and any direct exception. Do not extend conclusions from the source audit beyond its recorded build. |
| Subscription delivery | Prefer `fetch` and import the local YAML retrieved over strict SSH. Do not treat the public `http://...:8443/<token>/clash.yaml` link as encrypted or publish it. If URL import is required, the user must explicitly accept cleartext bearer-token transport or provide an approved encrypted retrieval path. | The local YAML's protected file permissions and import result. A successful HTTP status from the public endpoint is not a confidentiality pass. |
| Recovery and disconnect | Keep a provider console and a known-good SSH session available during changes. If deployment fails, inspect the sanitized status and timestamped backups before any rerun; do not assume the script rolled back package/firewall/service changes. Verify TUN-off restores ordinary connectivity before quitting the tunnel client. | Failure checkpoint, preserved backup/state paths, recovery result and normal-connectivity observation. Do not delete the host-key pin, receipt or server identity state as an automatic cleanup step. |

## Reporting rule

Report each row as `passed`, `failed` or `not exercised`, with the evidence above. Offline tests can confirm local parsing, permission, host-key pinning, snapshot classification and source-policy invariants. They cannot establish VPS ownership, provider firewall behavior, a real SOCKS exit, IPv6/UDP containment, DNS privacy, browser/WebRTC behavior or successful recovery on a target server.
